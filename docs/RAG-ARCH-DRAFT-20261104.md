## Вопрос владельца
Полностью свой пайплайн с нуля vs существующие библиотеки/наработки.

## Рекомендация Квинта: гибрид
Не «с нуля полностью» и не тяжелый фреймворк. Собственный пайплайн
(чанкинг, метаданные, фильтры, фьюжн) на стандартных компонентах
(FTS5 + sqlite-vec + лёгкая эмбеддинг-модель).

Обоснование: sud-cli — offline-first, минимум зависимостей, fail-closed.
Весь индекс = один .db файл, переносим, бэкапится копией.

## Стек

1. **BM25 — SQLite FTS5.** Уже в SQLite 3.53 (есть на хосте),
   ноль новых зависимостей. Точные термины, номера статей/пунктов,
   реквизиты постановлений — профиль FTS5.

2. **Векторный индекс — sqlite-vec** (Apache-2.0, одна C-расширение,
   работает внутри того же .db, транзакционно с метаданными).
   НЕ Chroma (сервер, транзитивные зависимости) и НЕ Faiss
   (тяжёлая нативная зависимость, отдельный файл, вне транзакций БД).

3. **Эмбеддер — абстракция, default: лёгкая мультиязычная модель**
   (кандидат: multilingual-e5-small/base, 120–470 MB весов,
   через sentence-transformers). Опция: ONNX-runtime для облегчённого
   режима. Веса грузятся разово через прокси (RU-egress), далее офлайн.

## Доменная логика — своя (основной объём работ)

- **Парсеры:** постановления Пленума ВС/ВАС по пунктам, фабулы обзоров
  Президиума ВС. Никакая библиотека это не сделает.
- **Схема метаданных:** отрасль права, статья кодекса, дата редакции,
  статус (active / overturned / uncertain), источник, номер пункта,
  ссылка на чанк-родителя.
- **Pre-filter до поиска:** жёсткие WHERE-фильтры по метаданным
  ДО BM25/vector, не пост-фильтрация.
- **Fail-closed (Law Zero):** парсер не уверен в структуре → чанк
  в карантин, не в индекс. Только верифицированное попадает в БД
  (перекликается с IMPORT-POLICY.md).

## Анти-галлюцинационный слой

- Каждый выданный чанк = верифицированная цитата с точным реквизитом
  (документ, пункт, редакция).
- Статус overturned исключает чанк из выдачи на уровне запроса,
  не на уровне промпта.
- Генеративный слой не имеет права воспроизводить текст нормы
  без чанка-источника.

## Гибридный поиск

BM25 + вектор, слияние рангов — RRF (Reciprocal Rank Fusion),
~30 строк своего кода, без библиотек.

## Согласовано с colleague (04.11, через владельца): судьба утративших силу актов

**Решение: включать в базу с жёсткой временной разметкой, выкидывать нельзя.**

Юридическое обоснование (colleague):
1. **Темпоральность** (ст. 9, 10 УК РФ; ст. 422 ГК РФ): отношения регулируются нормами и разъяснениями, действовавшими в момент деяния/сделки; для длящихся отношений нужно знать толкование на тот момент и обратную силу новых пленумов.
2. **Аудит позиций оппонента:** суды/прокуроры нередко цитируют отменённые пункты из старых шаблонов (кейс: отменённый ППВС № 51); RAG с историей отмен даёт довод для апелляции («суд положил в основу разъяснение, утратившее силу»), без истории — агент «не узнает» цитату.
3. **Частичная отмена:** пленумы чаще отменяются по пунктам («признать утратившими силу п. 3, 7, 12, п. 15 изложить в новой редакции») — выбрасывать документ целиком = потерять оставшиеся действующие пункты.

Схема чанка (верифицированная legal):
```
doc_number, point, effective_from, effective_to, status, superseded_by
```
- **Дефолтный режим (95% задач):** жёсткий SQL-фильтр `WHERE status = 'active'` — отменённое физически не попадает в выдачу и контекст модели (защита на уровне запроса, не промпта).
- **Режим ретроспективы:** `sud-cli practice --as-of YYYY-MM-DD` или `--include-overturned` — чанк выдаётся с предупреждением `[УТРАТИЛО СИЛУ <дата>, заменено на <реквизит>]`.
